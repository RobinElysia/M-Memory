# 架构详解：总体设计

## 设计哲学

m-memory 的设计围绕一个核心洞察展开：**AI Agent 的记忆系统不需要记住每句话的每个字，
但需要能在正确的时间找到正确的信息，并能识别信息之间的矛盾**。

为此，我们采用了"刚柔并济"的混合架构：

- **刚性分桶** — 用动态聚类将海量记忆压缩为少量桶，桶的 Medoid 向量作为第一层粗筛索引。
- **柔性图边** — 在桶之间建立跨桶关联边，允许跨主题联想，但不复制节点。
- **双层检索** — Layer 1 用桶 Medoid + A 向量快速定位候选集，Layer 2 用 C 向量精确排序 + 冲突消解。

## 数据流全景

```
INGEST（写入路径）
─────────────────
用户对话
  │
  ├─→ 提取 A (摘要) → embed(A) → 与所有桶 Medoid 比相似度
  ├─→ 提取 C (详情) → embed(C) → 存入向量索引（供后续搜索）
  │
  └─→ LLM 决策分桶 → 存入主桶 → 建跨桶边 → 更新 Medoid


SEARCH（读取路径）
─────────────────
用户查询
  │
  ├─→ embed(query) → Layer 1: 与活跃桶 Medoid 粗筛 → top_m 桶
  ├─→ Layer 1: 桶内 A 节点精筛 → seed nodes
  ├─→ Layer 1: 沿跨桶边 BFS 扩展 → 合并候选集
  │
  └─→ Layer 2: 加权重排序 → LLM 矛盾检测 → 标记过时 → 返回结果


CLEANUP（后台路径）
──────────────────
定时任务（默认 300s 间隔）
  │
  ├─→ 桶休眠检查 → 移除 Medoid 出活跃索引
  ├─→ 桶内矛盾扫描 → 标记过时节点
  ├─→ 话题漂移检测 → 移入冷存储
  └─→ 桶分裂检查 → 拆分过大的桶
```

## 核心算法复杂度

| 操作 | 时间复杂度 | 空间复杂度 | 说明 |
|------|-----------|-----------|------|
| 摄入 (ingest) | O(B + K·log K) | O(D·B) | B=桶数, K=桶内节点数, D=向量维度 |
| 粗筛 (bucket screen) | O(B·D) | O(B) | 遍历所有活跃桶 Medoid |
| 精筛 (in-bucket search) | O(K·D) | O(K) | 桶内向量检索 |
| 图扩展 (graph expansion) | O(E·H) | O(V) | E=跨桶边数, H=最大跳数 |
| 冲突消解 | O(N·log N + 1 LLM) | O(N) | N=候选节点数 |

## 线程安全

当前版本为**单线程设计**。BucketManager 和 RetrievalEngine 的内部状态
（`_buckets`、`_nodes`）未加锁。多线程场景需要外部同步。

CleanupScheduler 支持两种运行模式：
- **同步线程**：`start_sync()` 启动 daemon 线程，不阻塞主路径
- **异步协程**：`start_async()` 启动 asyncio Task

## 与 RAG 的对比

| 特性 | 传统 RAG | m-memory |
|------|---------|----------|
| 索引单位 | 文档块 (chunk) | 对话轮次 (MemoryNode) |
| 组织方式 | 扁平向量库 | 动态聚类桶 + 图 |
| 检索方式 | 单层向量搜索 | 双层：桶粗筛 → 桶内精筛 → 图扩展 |
| 冲突处理 | 无 | LLM 检测 + 过时降权 |
| 维护 | 手动 | 自动：休眠/唤醒/漂移检测 |
| 可解释性 | 低（纯向量分数） | 高（桶归属 + 图路径 + LLM 理由） |
